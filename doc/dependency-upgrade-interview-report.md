# 前端依赖现代化专项面试报告

## 项目背景与目标

这是一个基于 Vue 3、Vite、Pinia、Vue Router、Vant、UnoCSS 和 Workbox 的 PWA 计分应用。项目依赖长期未升级，缺少自动化测试，生产依赖审计发现 15 个漏洞（7 个高危、5 个中危、3 个低危），同时 Excel 导出模块使结果页产物接近 956 kB。

我的目标不是“把版本号全部改成 latest”，而是在可验证、可回滚的前提下完成依赖现代化：采用最新稳定版本，替换不再适合继续使用的库，保护用户本地数据兼容性，并把升级规则固化到 CI 和包管理配置中。

## 核心方案

### 1. 先建立基线，再分阶段升级

我先记录漏洞、构建产物、PWA 预缓存体积和核心业务行为，再按“测试护栏 → 基础工具链 → Vue 生态 → 业务依赖 → CI 收口”的顺序实施。每一阶段都执行 lint、测试、构建和依赖审计，避免多个破坏性变更叠加后难以定位。

“最新稳定”被定义为：正式版、满足 peer dependency、许可证可接受，并已发布至少 7 天。项目通过 pnpm 的 `minimumReleaseAge: 10080` 固化冷静期，降低刚发布版本和供应链投毒的风险。

### 2. 用测试保护高风险兼容点

项目原先没有测试。我引入 Vitest、Vue Test Utils 和 jsdom，补充 6 个测试文件、9 个测试，覆盖：

- 计分的加、减、重置逻辑；
- Pinia 持久化数据恢复和 store ID 兼容；
- 路由守卫；
- Radash 的分组与排序行为；
- iPad 桌面 UA、混合指针设备等平台判断；
- Excel 数据映射、多工作表及真实 XLSX Blob 生成。

这组测试重点保护“升级后最容易静默出错”的数据和业务契约，而不是只追求覆盖率数字。

### 3. 有选择地保留、替换依赖

- 保留 Radash，并从 12.1.0 升级到 12.1.1，使用测试锁定 `group`、`sort` 的现有语义。
- 用 `write-excel-file` 替换 ExcelJS，保留多工作表、样式、合并单元格和列宽能力，同时移除其高风险传递依赖。
- 移除 `ua-parser-js`。其 v2 许可证不适合本项目，旧主版本又不是长期理想选择；改为优先使用 pointer capability，辅以窄范围 iOS 判断，减少脆弱的 UA 嗅探。
- 移除 `normalize.css`，只在项目样式中保留实际需要的 reset。
- 移除未产生实际价值的 `unplugin-auto-import`，改用显式导入，减少隐式行为和维护面。

同时完成 Vue 3.5、Pinia 3、Vue Router 5、Vite 8、ESLint 10 flat config、UnoCSS、Vant、PWA/Workbox 等升级，并将 Node 24、pnpm 11.10.0 固定到本地约束和 CI。

## 验证结果

| 指标 | 升级前 | 升级后 |
| --- | ---: | ---: |
| 生产依赖已知漏洞 | 15 | 0 |
| ResultView 产物 | 约 956 kB / gzip 276 kB | 约 90 kB / gzip 26 kB |
| PWA 预缓存 | 1408.78 KiB | 548.17 KiB |
| 直接运行时依赖 | 14 | 9 |
| 自动化测试 | 0 | 6 个文件、9 个用例全部通过 |

最终 `pnpm install --frozen-lockfile`、`pnpm lint`、`pnpm test:run`、`pnpm build`、peer dependency 检查、生产依赖高危审计和 `git diff --check` 均通过。结果页原始体积下降约 90.6%，PWA 预缓存下降约 61.1%。CI 现在会依次执行锁文件安装、lint、测试、高危漏洞审计和构建，避免项目再次回到“多年不敢升级”的状态。

## 风险控制、取舍与遗留项

我刻意没有借依赖升级扩大到业务架构重写；持久化 store ID、字段结构和用户数据读取路径保持兼容。大版本升级按阶段隔离，锁文件和测试提供明确回滚边界。

当前仍有两项需要如实说明：第一，本地环境没有可用浏览器实例，因此已验证 PWA manifest 和 service worker 可访问，但尚未完成完整的视觉与点击回归；上线前应补一次真机/浏览器冒烟。第二，PWA 子构建仍报告一条 `inlineDynamicImports` 弃用警告，构建不受影响，判断来自当前 Vite/PWA/Workbox 适配层，应持续关注上游版本并在修复后移除兼容配置。

## 面试官可能追问

**为什么不直接执行一次全量 `pnpm update --latest`？**  大版本升级的风险不只来自 API，还来自 peer dependency、许可证、持久化数据和构建插件协作。分阶段升级能让每次失败都对应一个较小的变更集。

**为什么用发布时间冷静期，而不是永远追最新？**  latest 只代表维护者当前标记的正式版，不代表已经经过生态验证。7 天冷静期兼顾安全更新速度和供应链风险；紧急安全修复可以评估后做有记录的例外。

**为什么替换 ExcelJS？**  它是漏洞和大体积的主要来源，而项目只需要有限的表格生成能力。替换后保留业务所需特性，并通过真实文件生成测试证明不是“为了减包而降级功能”。

**为什么 Radash 不移除？**  它仍在维护，现有调用清晰且替换收益有限。更合理的决策是升级到稳定最新版，用测试固定语义，而不是为了减少依赖数量制造无价值重写。

**如何避免以后再次积累技术债？**  固定 Node/pnpm 版本和发布冷静期，在 CI 设置 lint、测试、构建、peer dependency 与漏洞门禁，并建议配合定期依赖 PR、小批量合并及季度人工复核。

## 3—5 分钟口述版

我负责的是一个 Vue 3 PWA 项目的依赖现代化。这个项目依赖长期没有升级，而且原来没有自动化测试。开始时我先做了基线审计：生产依赖共有 15 个已知漏洞，其中 7 个高危；结果页因为引入 ExcelJS，单个产物接近 956 kB，PWA 预缓存约 1.38 MiB。

我没有直接把所有依赖改成 latest，因为依赖升级真正难的不是改版本号，而是控制大版本 API、peer dependency、许可证、用户本地数据和构建插件之间的组合风险。我先定义了升级规则：只采用正式稳定版，满足许可证和兼容性要求，并默认经过 7 天发布冷静期；这个规则直接写进 pnpm 配置，而不是只停留在文档里。

接着我先补测试护栏。项目最重要的风险不是页面能不能打开，而是计分是否正确、Pinia 持久化数据能否恢复、路由是否正常、导出的 Excel 是否可用。因此我引入 Vitest，一共补了 6 个测试文件、9 个用例，覆盖计分、持久化、路由守卫、平台识别、Radash 分组排序，以及真实 XLSX 文件生成。

实施上我按工具链、Vue 生态和业务依赖分阶段升级。Vue 升到 3.5，Pinia 升到 3，Router 升到 5，Vite 升到 8，ESLint 迁移到 10 的 flat config，并统一使用 Node 24 和 pnpm 11。Radash 仍然维护且现有用法合理，所以我选择保留并升级到最新版，再用测试锁定行为。

依赖治理里有两个关键判断。第一，ExcelJS 带来了主要的传递漏洞和包体积，但项目只用了有限的导出能力，所以我用更轻的 `write-excel-file` 替换，并保留多 sheet、样式、合并单元格和列宽。第二，`ua-parser-js` 新主版本的许可证不适合项目，继续停留在旧主版本也不是长期方案，所以我把 UA 嗅探改成能力检测，只对 iOS 做很窄的兼容判断。另外还移除了 normalize.css 和没有实际收益的自动导入插件，缩小维护面。

最后的结果是：生产依赖漏洞从 15 个降到 0；结果页产物从约 956 kB 降到 90 kB，下降约 90.6%；PWA 预缓存下降约 61.1%；直接运行时依赖从 14 个降到 9 个。lint、9 个测试、构建、peer dependency 和高危漏洞审计全部通过。我还把这些检查加入 CI，让这次升级从一次性清理变成持续治理机制。

我也会主动说明边界：当前还缺一次真实浏览器和真机的完整视觉、点击回归；PWA 子构建有一条上游适配层的弃用警告，但不影响构建，需要持续跟进。这个项目让我最有价值的经验是，优秀的依赖升级不是追求版本最新，而是用基线、测试、分阶段变更和自动化门禁，把不确定性变成可验证、可回滚的工程过程。

## 60 秒精简版

我完成了一个 Vue 3 PWA 的依赖现代化。升级前项目没有自动化测试，生产依赖有 15 个漏洞，结果页产物约 956 kB。我先定义“最新稳定”为正式版、兼容许可证和 peer dependency、默认发布满 7 天，再补充计分、持久化、路由、平台识别、Radash 和 Excel 导出的 9 个测试。

随后分阶段升级 Vue、Pinia、Router、Vite 和 ESLint。Radash 保留并升级最新版；ExcelJS 替换为更轻的导出库；`ua-parser-js` 改为能力检测；同时移除无效的 normalize 和自动导入依赖。最终生产漏洞归零，结果页产物下降约 90.6%，PWA 预缓存下降约 61.1%，所有 lint、测试、构建和依赖检查通过，并全部固化进 CI。整个工作的核心不是更新版本号，而是建立一套可验证、可回滚、可持续的依赖治理机制。
